# whatsapp-service

سيرفر Node مستقل (Express + Baileys) يوفّر اتصال واتساب حقيقي + نظام OTP
لمشروع uco-pickup. **منفصل تمامًا عن الموقع الثابت** (`../`) لأن الموقع
يُصدَّر كـ GitHub Pages بدون سيرفر خلفي، بينما اتصال واتساب (Baileys) يحتاج
عملية Node شغالة باستمرار 24 ساعة — نفس النمط المستخدم سابقًا لمشروع رحال.

## التشغيل محليًا

```bash
npm install
cp .env.example .env   # عدّل القيم حسب الحاجة
npm run dev
```

أول تشغيل يطبع رابط `/whatsapp/status` — افتحه (مع هيدر `x-admin-token`) وامسح
رمز QR بواتساب هاتفك (إعدادات → الأجهزة المرتبطة) لربط الرقم.

## النشر على Railway

1. أنشئ مشروع جديد في Railway واربطه بهذا المجلد (`whatsapp-service/`) فقط —
   ليس جذر المستودع كامل (فيه مشروع Next.js آخر بجانبه).
2. أضف **Volume** بمسار ثابت (مثلاً `/data`) واضبط `WA_SESSION_DIR=/data/wa-session`
   و`WA_NOTIFY_SESSIONS_DIR=/data/notify-sessions` — بدون هذا، أي عملية نشر
   جديدة (redeploy) تمسح كل الجلسات (النظامية وجلسات المجمّعين) وتطلب مسح
   QR من جديد للكل.
3. اضبط باقي متغيرات البيئة من `.env.example` (خصوصًا `ADMIN_TOKEN` و
   `ALLOWED_ORIGIN` = رابط GitHub Pages للموقع).
4. تأكد إن أمر التشغيل الفعلي هو `npm run build && npm start`
   (بناء مرة واحدة ثم `node dist/index.js` كعملية واحدة مستمرة) — **لا تستخدم
   وضع `--watch` في الإنتاج أبدًا**، لأن Baileys يعدّل ملفات الجلسة باستمرار
   وأي أداة مراقبة تعتبر هذا "تغييرًا بالكود" وتعيد التشغيل بحلقة لا نهائية.

## نقاط الـ API

- `GET /health` — فحص حياة عام، بدون حماية.
- `GET /whatsapp/status` *(محمي بـ `x-admin-token`)* — حالة الاتصال، رقم
  الهاتف المرتبط، رمز QR (كـ data URL) عند عدم الاتصال، وعدادات
  (أُرسل/نجح/فشل).
- `POST /whatsapp/logout` *(محمي)* — قطع الاتصال ومسح الجلسة لربط رقم جديد.
- `POST /otp/send` `{ phone }` — عام (غير محمي)، يرسل رمز تحقق عبر واتساب.
  محدود بـ: تبريد 60 ثانية بين الطلبات لنفس الرقم، صلاحية الرمز 5 دقائق،
  5 محاولات تحقق كحد أقصى.
- `POST /otp/verify` `{ phone, code }` — عام، يتحقق من الرمز.

### إشعارات المجمّعين (رقم منفصل عن OTP لكل مجمّع)

كل مجمّع يقدر يربط رقم واتساب خاص فيه (منفصل تمامًا عن رقم OTP النظامي
الواحد) من صفحة `/collector/settings` بالموقع، لإرسال إشعار حقيقي للمولّد
عند تأكيد كل عملية سحب. جلسة Baileys مستقلة لكل `collectorId`.

- `GET /notify/:collectorId/status` — عام، بدون حماية admin token (لوحة
  المجمّع نفسها بلا تسجيل دخول حقيقي بعد). يُنشئ الجلسة تلقائيًا أول مرة
  ويرجّع رمز QR لو غير متصلة.
- `POST /notify/:collectorId/logout` — عام، يقطع الاتصال ويمسح الجلسة لربط
  رقم جديد.
- `POST /notify/send` `{ collectorId, phone, text }` — عام، يرسل رسالة نصية
  من رقم المجمّع المرتبط إلى رقم المولّد. يفشل برسالة واضحة لو المجمّع ما
  ربط رقم بعد.

## معروف وغير مُعالَج بعد

- لا يوجد حد لعدد الطلبات لكل IP على `/otp/send` — فقط تبريد لكل رقم هاتف،
  فممكن نظريًا مهاجمة النقطة بأرقام مختلفة كثيرة. اقبل هذا للنموذج التشغيلي
  الحالي، لكن راجعه قبل أي استخدام فعلي حساس.
- الرموز تُخزَّن بالذاكرة فقط (`Map`) — تُفقد عند إعادة تشغيل السيرفر
  (وليس عند إعادة نشر عادية بدون تعطّل).
- حد أقصى 25 جلسة إشعارات متزامنة (`MAX_CONCURRENT_SESSIONS` في
  `notify.manager.ts`) لمنع استنزاف الموارد من نداءات `/notify/:collectorId/status`
  بمعرّفات عشوائية — لا يوجد تحقق فعلي إن `collectorId` مجمّع حقيقي مسجّل
  بالنظام (السيرفر ما له اتصال بقاعدة بيانات Supabase).
